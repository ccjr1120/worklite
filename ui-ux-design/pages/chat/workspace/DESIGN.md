## Purpose

Converse with the protected master Agent through Web, configure its capabilities and communication channels, and inspect complete stored conversations and execution evidence from every implemented channel.

## Primary Task

Send a request and read its response. Action budget one: submit the composer. A material pending question adds one answer action. Team questions, exact Command grants, Run controls and recovery stay in Chat's task card; Team configuration, work roles and memories are managed by asking Chat. Coding, project investigation and local command tasks delegate directly to Codex without a WorkLite authorization step. Chat exposes only platform orchestration operations. Cancelling the current turn is one separate action, available while running or waiting for an ordinary answer. Channel configuration is an independent goal: one activation for Feishu QR registration, or field input and one save for an existing application because credentials must come from the operator. Inspecting a saved conversation costs one selection; opening its complete record pane is one separate inspection action.

## Layout

A periodic active-work reply appears as a neutral progress card within the assistant reading column, collapsed to one compact line by default: the state name “工作进展”, the in-progress item count, the most recently changed item's title and the report timestamp, with a trailing chevron toggle at status-line height. Expanding the card reveals the captured work list — each project task, Team Run or Workflow Run as a row with its kind label, title, run id, stage and progress text beside its shared status badge — followed by the model's full Markdown summary. Expansion is one conversation-level choice shared by every progress card, so a later periodic report keeps the reader's selection; the choice resets to collapsed when the conversation changes or the page reloads. The server supplies a typed `progressReport` snapshot on both message deltas and the persisted assistant message, so the first streamed text and reloaded history use the same card; its items carry optional `stage`, `progress` and `updatedAt` presentation fields that the reminder text and its dedupe signature never depend on. Ordinary replies retain their unframed layout. The card uses shared surface, border, typography and status tokens in both themes; the collapsed line truncates its title and the expanded rows wrap, without introducing a new design token.

A full-height conversation-only Chat workspace has a stable context bar, unfiltered server conversation history on the left, and an unframed transcript with a floating composer card on the right. The complete evidence pane opens within the transcript area. Below `md`, history opens in a labelled Sheet. The shell hides command search on `/chat`; one page-owned settings icon in the context-bar action area opens the Chat settings Dialog. Both themes use shared neutral surfaces and semantic tokens.

The conversation list separates live work from history. An **In progress** group pinned at the top holds conversations whose status is running, waiting for input, or queued; each row carries a leading status mark (an animated brand live dot for running, a pulsing amber mark for waiting, a dashed mark for queued) and a `brand-subtle` tint. Below it, **Today** and **Earlier** groups hold settled conversations with quiet leading marks: a green check for completed, a red cross for failed, a slash for cancelled. Group headers show a count. A conversation moves between groups with a short fade as its server status changes. The conversation header shows the shared status badge for the selected conversation, and the sidebar Chat destination shows the live dot while the In progress group is non-empty. The complete evidence pane opens below the conversation header and scrolls within its own region; ordinary replies stay readable. Below `md`, the conversation list opens in a labelled navigation drawer, preserving the full transcript width. Both themes use shared semantic tokens; ordinary icons and secondary actions stay neutral. Chat replaces Home's bottom composer and the shell floating Chat Bot.

A project task tool call remains one inline disclosure. Its collapsed row shows the first line of the captured goal, shared task status, project directory, model and executor (Codex or Claude Code); a live task also shows a server-derived stage chip (starting, working, responding, or waiting — never a fabricated percentage), its latest persisted activity and total activity count rather than a context-free running label. Expansion reveals a metadata grid, phase counts and executor activities grouped per phase or tool call into foldable sections with text rendered as Markdown, journaled operations retained from tasks recorded before native executors, the Markdown result, a red failure reason, and raw task JSON only behind a second collapsed disclosure. The expanded list loads the latest 20 activities first and pages the full persisted history on demand, with a visible note when the server truncates an oversized history. Each operation's full retained input and output loads when its own detail control opens; the task and execution snapshot never carry those result bodies. The transcript does not render raw JSON merely because the task row is expanded.

The Dialog uses internal Configuration, Channels and Memories sections, in that order, switched through a slim left section rail of icon-and-label items rather than top tabs; the selected item uses the shared navigation `brand-subtle` pill with a `brand-text` icon, and below `sm` the rail collapses to accessible icon-only buttons. Configuration owns the model, one Executors field group (a single `fieldset` whose legend names it, holding the Claude Code and Codex default-model Selects as labelled rows), the extension prompt and the summarize prompt. Channels lists only channels that need setup, currently Feishu; the built-in Web channel is not listed because direct Web conversation needs no registration, and its runtime behavior is unchanged. There is no Skill or MCP server selection: project executors only receive a model choice from Chat, and custom capabilities do not execute in Chat. Memories lists the workspace long-term memories Chat saved during conversations, grouped by category in the contracts-declared order with a pill filter row (all plus each present category); each group header carries a badge naming the category's injection behavior (始终注入 for rule/preference, 按需读取 for the rest, from the shared `CHAT_MEMORY_CATEGORY_META`), and each entry shows its full text, last-updated time, one category Select and one delete action; saving and correcting memory content happens in conversation, not in this Dialog. The Dialog has one fixed height, `min(40rem, 85vh)`, independent of the active section; the header and section rail stay in place, and the active section scrolls within the remaining region with a stable scrollbar gutter, so switching sections changes only the content and never resizes, re-centres or horizontally shifts the Dialog. The main workspace height and conversation content remain stable while the Dialog opens and closes. Cancelling uses the existing neutral Send-or-Stop target while executing. While waiting for an ordinary answer, one neutral Cancel button sits beside Send. Cancel progress stays on that control; input and conversation content remain in place. No new design token is introduced.

## Interaction Contract

- Automatic progress feedback costs zero actions. The roughly 90-second active-work check and visible-change signature remain authoritative; its model-only note still requests a brief direct reply. Web renders that reply as a card from the explicit report metadata, never by parsing the reply text. The card's collapsed line already carries the count and latest-change signal; expanding the work list is one optional disclosure action per conversation, shared by every progress card and reset when the conversation changes or the page reloads — it is never paired with a commit control. Streaming keeps the same card and caret, while history retains the report-time titles, statuses and timestamp as a snapshot rather than polling old reports. Feishu and WeChat continue consuming the unchanged reply text, a complete readable sentence independent of the Web collapse state. No refresh, confirmation or extra task action is added.
- Independent task feedback: a Chat turn's completion or failure does not settle a delegated Team Run. Its task card automatically observes the bound Run status, displays the Run's current phase and server-derived completion percentage, retained failure reasons and pending questions, and opens read-only evidence from the task-detail link. A waiting question appears inline in the Chat task card with its answer field; non-project-executor questions also expose a separate structured exact-command field that only accepts user-entered exact strings. The model cannot submit or infer grants. The same card owns pause, resume, cancel, retry of the server-declared failed active task, and operation recovery controls. Team configuration, role directory, working practice and Team memories are changed by asking Chat, which invokes protected typed operations. A dispatched Team Run's terminal success or failure is additionally reported once by an automatic assistant reply in the same conversation; cancelled Runs and Team questions are not auto-reported. Read failures remain local to the task card. Failed submissions without a task reference remain visible in chronological order.
- Project task progress text: display the latest complete public executor message below its disclosure header while no final result is available, including after failure or cancellation. Expansion retains public messages in the existing activity list. The header names the captured executor, and existing semantic surfaces, status cues and reduced-motion behavior apply in both themes. No new control or action is added.

- Chronological transcript: messages, tool calls including project task disclosures, Team, Workflow and upgrade task cards (failed dispatches included), a just-started Workflow run, received Feishu messages awaiting execution, the pending question, the summary divider and the cancelled or failed turn note all appear in one sequence ordered by their own timestamps. The summary divider is a persisted state marker, not a message: it renders as a full-width hairline with a centred muted label inside the reading column and stays in place across reload. A divider whose message carries the summary text pairs the label with one expand toggle that reveals the full summary in place and collapses it again; a divider without content stays a plain marker with no action. The persisted user echo of the `/summarize` command renders as an ordinary user message immediately before its divider. No category is pinned to the end of the transcript; only unsent queued messages, which have not happened yet, follow the sequence.
- Unfinished execution pin: a Team, Workflow or upgrade task card or project task disclosure that is still queued, running, paused or waiting for input keeps its chronological place. When the reader scrolls it above the visible transcript, a compact pinned bar at the top of the transcript area lists it as one row with task name, shared status mark and latest progress; activating the row scrolls back to the original card and expands it. A row leaves the bar when its card returns into view or its task settles. Rows follow chronological order; beyond three, the bar shows the remaining count as one disclosure. The bar never reorders, duplicates or hides transcript content, and needs no manual refresh.

- Redeployment: sending an explicit request to redeploy WorkLite is the single activation and authorization. Show its persisted phase, version and outcome in the existing task region of that conversation; update automatically and retain the last state during cutover. No second confirmation, manual refresh or automatic retry of deployment is offered. Initial managed installation remains an operator operation. Both themes use the existing neutral task region and semantic running/error states.
- New conversation intent: Chat asks a typed pending question after recognizing the user's request and shows one contextual “新对话” button. Clicking creates and selects the new persisted conversation; old history and task evidence remain. This action is absent from ordinary replies and disappears after acceptance. No permanent reply menu or text-command requirement is introduced.

- Retired command question: a never-started Shell call waiting on removed per-command authorization is cancelled by the server, retaining its history and clearing the invalid question. The server persists the resulting snapshot for replay; later messages return to normal dialogue with no manual stop instruction or extra recovery button is required. Reserved effects still use explicit recovery.
- Execution boundary: coding, project investigation and local commands delegate to a project executor (Codex or Claude Code); collaborative work uses Team and automation uses a published Workflow. Chat has no direct host tools or arbitrary Skill/MCP calls. Historical Shell disclosures and uncertain-effect recovery remain available without starting new Commands.
- Live observation: keep the transcript, composer, expanded tool rows and reader scroll mounted during background updates. One SSE connection observes both running and waiting states; initial connection starts at the latest snapshot and following deltas. Older snapshots cannot roll back current content, and repeated event delivery cannot append a delta twice.
- Independent project task: keep progress, result and full execution evidence in the originating conversation. Reuse the existing tool disclosure and answer region. The executor starts directly from the requested project task without a WorkLite proposal confirmation or command form; Team developer uses the same executors. An interrupted task fails without automatic replay. Stop cancels the task; uncertainty retains a visible recovery question. Ordinary dialogue and both themes retain their existing layout.
- Background project task: once a project task starts, its turn settles and the composer sends immediately instead of queueing, so the user can keep talking while the task runs. The execution SSE stays connected while any task of the conversation is active, and the task disclosure plus pinned bar keep updating. A live task disclosure shows one secondary compact “取消任务” action. A task question renders inside its own disclosure as the question text, an accessible textarea and a “回答” action; answers stay control-local with spinner and inline error, and the user may also answer in ordinary conversation. While the turn is settled but a task is active, the composer shows the existing square Stop control beside Send; activating it cancels every active task of the conversation through the same cancellation flow. When a task settles or asks a question, an automatic assistant reply reports it in the transcript without a user message. The conversation list treats a conversation with an active task as In progress.
- Image attachments: a Markdown image in an assistant reply, task progress text or task result renders inline inside the shared Markdown renderer, bounded to the reading column width and a 24rem height with rounded corners and a `border` outline. Images load lazily, carry the Markdown description as their accessible name, and add no control. When an attachment is missing or expired, the image is replaced by a compact inline placeholder on `surface-subtle` with a `border` outline, an image-off icon and the state text “图片已过期”, so the cue is not color alone. Both themes use the same semantic tokens; no new token is introduced.
- Project task evidence disclosure: expansion is one inspection action. The primary expanded content is structured task data; raw JSON remains a separate secondary disclosure and is serialized only when opened. The task view shows the latest 20 executor activities with phase counts; a retained historical operation fetches its complete journal result on demand. Long lists remain bounded without replacing or truncating the authoritative raw record.

- Cancel: use the existing cancellation API once, without a confirmation dialog. Running turns use the square control; ordinary waiting turns retain Send and expose one adjacent Cancel. The shared Send/Stop primitive composes its own click with the Tooltip-trigger click; forwarded wrapper props cannot overwrite cancellation. The control shows a spinner and “取消中” immediately and prevents duplicate cancellation with its own cancelling state. An in-flight send or answer cannot disable Cancel once the server execution exists. Cancelling invalidates older UI request completions; binding an execution id or reloading its snapshot does not count as switching conversations and cannot strand the send busy state. Preserve the draft and messages, pause queued sends and invalidate server conversation queries on completion. If the server returns uncertain-effect recovery, retain its question and recovery choices instead of claiming cancellation settled the effect. Failure stays beside the composer.

- Send and answer: use shared `POST /chat/dispatch`, stable submission ids and the existing master execution. `Enter` sends the composer and `Shift+Enter` inserts a newline; while an input method is composing text, `Enter` first confirms that composition instead of submitting it. Show an immediate response region; stream persisted Agent events. Keep partial replies on failure, with existing retry and cancellation controls. Show options only for the active pending question.
- Answered question: a Chat question that has been answered stays in the transcript as one exchange. The question remains a quiet text line with a neutral question icon inside the assistant turn that asked it, and the answer is an ordinary right-aligned user message at the time it was accepted. Both derive from the stored `ask_user` call, so earlier conversations show their exchanges too; the call never renders as a Skill script row. While the question is active, only the existing amber question note represents it. A question closed by cancellation or by accepting a new conversation keeps its question line without an answer.
- Answer submission: typing an answer or activating an option clears the composer immediately and shows the answer as a user message with reduced emphasis, followed by the existing working note, until the server accepts it. The accepted exchange replaces it without moving the reader. A rejected answer removes that message, restores the text to an empty composer and keeps the safe error beside the composer.
- History: the list shows every conversation from the first page of `GET /chat/conversations` (newest first), with server data as authority and no search, channel filter, or load-more control. Browser memory remembers only the selected id. Selecting a conversation silently restores its in-memory draft and queue without cancelling another execution. Accepted queued requests carry stable submission ids, so returning after a response was interrupted cannot create another turn. Navigation retains browser-session drafts/queues in memory; reload clears unsent input.
- New conversation: one action opens an empty Web composer; the first accepted request creates its server execution. Existing records stay available.
- Feishu conversation: identify the bound channel before submission. Web can continue its Agent execution; the adapter projects replies into the same Feishu-bound conversation. Non-project-executor Team Command grants require the user-entered exact-command field on the bound Chat task card and cannot originate from Chat prose or model tool arguments.
- Records: load the full execution snapshot, stored Agent events, inbound and outbound receipts, selected actions/forms, submissions, rendered outbound cards, safe errors and delivery identifiers. Reveal raw saved fields only on deliberate disclosure. Provide full text copy/download; never truncate evidence or model-returned reply content. Related Team/Workflow tasks link to their authoritative detail routes.
- Freshness: execution SSE and five-second conversation/record queries recover observable changes automatically, retaining current content and reader scroll. No manual refresh control. The history list renders the complete first page the server returns.
- Settings Dialog: the context-bar settings icon opens the Dialog on Configuration, the first section; `view=channels`, `view=configuration` and `view=memories` deep links do the same. Selecting an internal section updates the validated route value without replacing the selected conversation. Escape or the Dialog close affordance returns to `view=conversation`, restores focus to the settings control, and leaves the mounted conversation body unchanged.
- Memories: the Dialog's Memories section groups every saved long-term memory by category with a one-tap pill filter; each entry shows its full text and last-updated time, a category Select reclassifies it in place through `PATCH /chat/memories/:id`, and deletion is one control-local action per entry without a confirmation dialog. A failed delete or category update stays beside the list as an inline error. Saving and correcting memory content belongs to the conversation itself; the Dialog adds no text-edit control.
- Configuration: open the Dialog's Configuration section directly or from the unconfigured composer setup action. Save at the activated control, keep durable request failures beside it, and retain immutable per-turn configuration snapshots. New turns use the latest revision; answers/retries retain their accepted snapshot. The summarize prompt is one optional multiline text saved on blur through the same revision-checked channel; leaving it empty restores the built-in default prompt, and the saved value applies from the next `/summarize`.
- Channels: reuse the approved Feishu QR and manual setup interactions inside the Dialog's Channels section; the adapter owns identity, connection and platform-specific presentation. Web conversation needs no channel registration.
- Slash commands: retain `/new`, `/resume`, `/summarize` and `/log` as shortcuts for visible conversation capabilities. `/summarize` summarizes the current conversation with Chat's configured model (`POST /chat/conversations/:id/summarize`) and stays on the same page: the server replaces the execution's stored model context with the summary as its new starting point, records the command itself as a persisted user echo message, and appends a persisted summary divider to the visible history, so earlier messages remain readable above the divider while later turns continue from the summary below it. The divider's message carries the summary text, and its expand toggle reveals that text in place. The summarize request uses the summarize prompt from Chat configuration verbatim as the system prompt when one is set (no placeholders) and the built-in default otherwise. With no active conversation it reports a local error beside the composer. Summarize progress uses the existing working note; failure stays beside the composer. History comes from the server. Slash commands do not replace the Settings Dialog. Escape dismisses inner menus and selections; an open history Sheet or settings Dialog owns Escape and focus while open.

## States

| State | Behavior |
| --- | --- |
| Active-work progress | Render the typed report as a labelled neutral card, collapsed to one line with the in-progress count, latest-changed title and report time; its toggle expands the captured work rows (kind, title, id, stage, progress, shared status badge) above the model summary. Stream in place with a caret; retain partial text on failure through the existing transcript flow. |
| Historical progress | Persisted reports retain the same card and report-time snapshot after reload. Messages without report metadata retain their existing presentation. |
| Team task | Observe the bound Run separately from Chat; show status, phase, progress and failure. Waiting questions, exact-command grants, Run controls and uncertain-operation recovery appear on the bound task card. The details link opens read-only Run evidence. Team administration is requested through Chat. A terminal Run is reported once by an automatic assistant reply. Retain cached state and show a local error when a read fails. |
| Failed dispatch | Keep the submitted message and safe error visible even when no task reference was created. |
| Redeployment | Show preparation, preflight, handoff, switch, recovery and terminal outcomes in the same conversation; reconnect after cutover without resubmitting. A proposal waits for an explicit redeploy request rather than a confirmation button. |
| Historical Shell call | Keep stored command evidence and explicit interrupted-command recovery inspectable; new direct Shell execution is unavailable. |
| Project task | Show executor, task state and persisted Command references in the existing execution disclosure; the captured task and any pending question remain visible and task-bound across reload. |
| Background project task | The turn is settled and the composer sends normally; the live disclosure offers Cancel task, a task question offers an inline answer, and the composer offers Stop for all active tasks. Cancel and answer failures stay beside their control. |
| Pinned unfinished execution | While an unfinished card or project task disclosure is scrolled above the transcript, show its compact row in the pinned bar with live status; remove the row when it returns into view or settles. |
| Loading | List and transcript skeletons keep the shell and conversation body stable; Dialog evidence and setup loading stay local. |
| Empty | Empty Web conversation shows the composer; no fixed capability or mode menu. A channel without records states it has no conversation yet. |
| Error | Preserve the selected transcript and show safe errors beside the affected send, configuration, channel or records action. |
| Cancelling | Keep draft and messages, show Cancel progress on the activated control and pause queued sends. |
| Waiting for Team input | Keep the answer control in the bound Team task card; exact Command grants use a distinct structured user field. Other Chat questions keep their existing answer controls. Unresolved Team operation recovery stays in that task card. |
| Answer sending | The submitted answer appears at once as a reduced-emphasis user message followed by the working note; the composer is empty and editable. A Team task answer keeps its exact-command field separate from message prose. Failure restores the answer and grant fields and shows the error beside the task card. |
| Answered question | The question line stays in its assistant turn and the answer stays as a user message, in chronological order, after reload and in older conversations. |
| Busy | Keep draft editable, preserve existing FIFO queue behavior, show concise inline processing and local disabled/busy controls. |
| Offline | Retain current data, show reconnect state and resume existing streams without resubmitting requests. |
| Image attachment | The image renders inline within the reply column; an expired or missing attachment shows the “图片已过期” placeholder in its place. |
| Long content | Full message body wraps. Evidence uses bounded scrollable full text with copy/download. Only conversation titles/previews truncate. |
| Channel waiting | A received Feishu message awaiting an execution remains visible with receipt status; queued messages do not disappear because they have no execution yet. |
| Codex operation detail | Show control-local loading for the selected operation, then its complete retained input and output; keep the summary visible on failure and offer the same control to retry the read. |
| Summary divider | Show the persisted marker after reload. A divider carrying the summary text starts collapsed and toggles the full summary in place through its expand action; one without content shows no action. |

## Accessibility

Progress cards are articles named by their visible heading; their timestamp uses a semantic `time`, statuses retain shared text and non-color cues, and streaming uses `aria-busy` without announcing every token. The collapsed row is one button with an accessible expand/collapse name; it exposes `aria-expanded`, controls the detail region by id, and shows the shared visible focus ring. The detail region appears with the shared fade and inherits the reduced-motion behavior.

The settings control, Dialog heading, settings section rail items, history controls, input and Cancel have accessible names and visible shared focus rings; the rail keeps a text label at `sm` and above and an accessible name on its icon-only form below it. The Dialog traps focus, closes on Escape and returns focus to its activating control. Cancel uses icon and text state, and its spinner respects reduced motion. Pending answers remain keyboard reachable. State updates do not move focus or scroll the reader away from earlier messages. Project task disclosure triggers, operation detail/retry controls and the secondary raw-JSON trigger expose their expanded state and accessible names. The summary divider keeps its labelled separator role free of interactive content, and the expand toggle below it exposes `aria-expanded` and controls the summary region by id. The pinned bar is a labelled region; each row is a keyboard-reachable button naming its task and status, and returning to a card moves focus to it without animation under reduced motion.
