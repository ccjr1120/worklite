## Required AI Workflow

Before starting any task, read `AGENTS_WORKFLOW.md` and follow the applicable workflow defined there. Do not begin work directly without using that workflow.

## Compatibility Policy

When changing routes, APIs, configuration, or other public project behavior, the default implementation does not preserve legacy compatibility. Do not add redirects, aliases, adapters, migrations, or other compatibility layers unless the user explicitly requests them. When compatibility is intentionally omitted, call out the resulting impact in the handoff.

## Minimal Implementation Policy

Implement only the smallest direct change required by the confirmed request. Do not proactively add validation, limits, compatibility layers, abstractions, fallback behavior, security hardening, or adjacent UX changes unless they are explicitly requested or required by an existing project rule.

When an out-of-scope concern is discovered, mention it briefly instead of expanding the implementation.

## Development Verification

Do not run tests, test scripts, diagnostic scripts, builds, development or start servers, browser checks, `curl` requests, `pnpm typecheck`, or other verification commands unless the user explicitly instructs you to run that specific command or check in the current request. Do not perform verification proactively.

Deployment replacement must pass a preflight gate: compile and start the new deployment on isolated resources, verify readiness, and only then stop or kill listeners on the target ports. If preflight fails, leave the existing target services untouched.

Do not automatically start, stop, restart, replace, or reconfigure running WorkLite server processes during implementation or verification. If a required service is unavailable or requires a restart, ask the user for explicit authorization for that lifecycle operation. Once the user explicitly authorizes it, you may perform the authorized operation, subject to the deployment preflight gate above.

By default, perform troubleshooting, investigation, and verification exclusively against the Web-only development profile: Web port `3390`, proxying to the managed deployment API port `23391` and Portkey Gateway port `23392`. Development has no separate local data directory; its persistent state is deployment-owned under `.data/deployment/`. Direct access to files and databases under `.data/deployment/` is permitted within the user task without separate authorization. When synchronizing Workflows, inspect every model reference in the source graph against the deployment model catalog and replace local model ids with the correct deployment-supported equivalents before publishing; do not publish a graph that references an unavailable model. Do not manage running WorkLite server processes without the user's explicit authorization.

## UI/UX Documentation

`ui-ux-design/README.md` is the source of truth for page structure, shared UI architecture, implementation sequencing, and page-level acceptance criteria. Store route specifications as `ui-ux-design/pages/<area>/<page>/DESIGN.md`, multi-page flows as `ui-ux-design/flows/<flow>/DESIGN.md`, and non-route surfaces as `ui-ux-design/surfaces/<domain>/<surface>/DESIGN.md`. Do not recreate a parallel page-specification directory.

Every `DESIGN.md` follows `ui-ux-design/TEMPLATE.md` in its section order and records a declared action budget, a per-state table, a copy inventory, and a dated Coverage Status listing the differences found against the implementation. Coverage Status is a verification result; do not restore a uniform unaudited placeholder.

`ui-ux-design/shared/interaction-contract.md` governs how many actions a task may cost: one activation point per goal, no preparation control paired with a commit control, no manual refresh for staleness the server can observe, control-local progress, and remembered input reapplied silently. `ui-ux-design/shared/copy-standards.md` governs which strings may exist: every string is an action, a state, a constraint, or a recovery, and text made obsolete by automation is deleted in the same change, in every locale.


## Durable Corrections

Chat owns troubleshooting evidence, task dispatch and progress reporting. It can independently delegate an authorized project task to a project executor, Codex or Claude Code, through its conversation-owned `project_task`, without Team planning, intake, queue or Run dependencies. The task names an executor only when the user does; otherwise Chat configuration's `defaultExecutor` (initially `claude`) applies. The task model resolves from the task's model parameter, then Chat configuration's per-executor `defaultExecutorModels` declaration, then the executor's own local default; the declarations are set or cleared per executor (Claude Code requires `anthropic/messages`, Codex requires `openai/responses` or `codex/responses`; saving rejects an incompatible protocol), and the captured launch records the effective model and its source. Team remains the collaborative execution and independent-review capability. Chat only orchestrates existing platform capabilities. Coding, repository investigation and local commands go directly to its conversation-owned project executor; collaborative work uses Team intake and automation uses published Workflows. Chat has no direct read, glob, grep, bash or arbitrary user Skill/MCP execution. Chat configuration has no Skill/MCP selection and its project executors receive no Skills or MCP servers from Chat (legacy Chat assignment rows stay stored but are ignored); only protected worklite-platform tools execute in Chat. Clear project requests require no additional WorkLite authorization. The executor captures the requested task and project instructions independently. Historical Shell evidence retains its absolute working directory, Command reservation and output/exit evidence; stream output older than seven days is pruned at startup to each Command's trailing 64 KB, while the Command record, lifecycle events and exit evidence persist. Never replay an interrupted command; recover a historical Shell call by adopting its terminal Command or marking it failed. Non-developer Team roles retain exact-command grants. Retire an obsolete Shell grant question automatically only when its bound call never reserved a Command: cancel the call and turn atomically, retain non-execution evidence and clear pending input and persist the current snapshot so later messages and replay are not trapped. Reserved effects keep explicit recovery. Capture the executor launch per task. There is no execution-engine fallback. Older Chat snapshots without a captured executor require a new task. Inspect previous task activity and the project's actual state before takeover and never automatically replay interrupted work. Attribute results to the actual project task or Team Run. Project tasks in a git repository run in per-task worktrees (`../<repository>-worklite-task-<id>` on branch `worklite/task-<id>`) and merge back through a serialized queue on success, with the worktree removed after a clean merge and retained on conflict or failure; same-directory parallelism has no cap, while non-git directories keep one active task per directory. Chat can list workspace-wide project tasks (`list_project_tasks`), subscribe another conversation's task for a one-shot completion report (`subscribe_project_task`), and actively watch a task (`wait_project_task`). Team Developer lanes use the same per-lane worktree isolation. Chat may propose a managed upgrade after inspecting produced changes; an explicit current WorkLite redeploy request authorizes deployment through the protected platform tool, and service replacement remains the independent runner's responsibility.

Chat owns conversation, configuration and Agent execution. Web, Feishu and any future WeChat integration are communication channels for that same Agent. Channel adapters own identity, connection, message receipt, platform rendering and delivery; Feishu cards do not define Agent behavior. The dedicated Chat workspace replaces the old Home composer and floating Chat Bot. Feishu configuration belongs under Chat → Channels, and Web must support direct conversation and full server-persisted channel history and execution evidence. Do not create a Feishu-specific Agent destination or implement a future channel merely because it appears in this architecture. Chat owns workspace-level long-term memory in the `chat_memories` table: the model saves, updates and deletes entries only through the protected worklite-platform memory tools, each accepted turn captures a bounded projection (newest-updated first, capped by entry count and total characters) into its immutable capability snapshot system prompt, and the Web Chat settings dialog lists and deletes entries. Memories are ordinary workspace data, not configuration revisions.

WorkLite has no first-use onboarding route family. Home derives first-use completion from persisted server resources, so a browser-state onboarding flow duplicates it with a weaker completion signal. Do not reintroduce `/onboarding` routes, an `onboardingStep` preference, or mock resource fixtures for a guided setup sequence.

State goals for generated writing, not layout. The user judges article output by whether it reads easily and says something clearly, and rejects fixed templates: banned-word lists, mandated section shapes, prescribed heading counts, and worked examples of allowed and forbidden forms all encode one person's taste as a rule and produce writing that reads as filled-in. Give the agent the reader outcome to aim at and let it choose the form. The exception is a constraint something downstream actually depends on, such as the single level-one heading and closed code fences the `worklite/artifact` publication gate rejects on, or the reference and link placement WeChat requires; keep those, state them as publication requirements, and keep them visibly separate from style so nobody has to guess which rules are load-bearing. When writing quality regresses, tighten the stated goal or the evidence behind it before adding another prohibition.

The article-writing Workflow serves the user's writing intent rather than GitHub alone. Treat input as an idea and derive relevant research questions and sources from it; GitHub is an optional evidence source. Planning and retrieval titles are provisional. The writer chooses the final title from the supported article, and the reviewer judges title/content fit rather than whether it repeats the input. Respect an exact title only when the user explicitly requires it.

Retrieval and generation aids assist the agent; they do not overrule it. A check that can block work must earn that power, because a wrong block costs the run its evidence while a redundant call costs seconds. Prefer returning a judgement to the agent as advice alongside the result it questions, and reserve hard refusal for bounding a runaway loop. Limits that silently discard material an agent already retrieved, such as tool-result truncation, are the most expensive form of strictness and must be sized so that retrieved evidence survives to the writer.

The Memory One visual reference uses brand color sparingly. Keep WorkLite surfaces, default icons, headings, and ordinary hover states neutral; reserve the blue brand token for primary actions, selected or focused states, active execution, and a small number of meaningful links.

When the user corrects agent behavior or states a durable repository-specific working preference, update this `AGENTS.md` in the same change so future work follows that correction.

WorkLite’s primary product services are Workflow automation and Home. Home has no global Workflow data source. Workflow scheduling is represented by at most one versioned `worklite/timer` graph node with a minimum 300-second interval; publishing synchronizes the internal `workflow_schedules` runtime projection, which is not independently editable. Only a Workflow’s immutable Dashboard node makes its latest successful published-version Run output available to Home. Eligible boards default to Uncategorized and may be organized in at most one database-backed Home category; those organization references do not persist output or change eligibility. Source-specific features such as Meegle todos are workflow use cases, not standalone products or navigation destinations. Chat is the protected master Agent capability with its own first-level Web workspace at `/chat`. Workflow Agent nodes are the only user-configurable Agent capability and own their public model id, system prompt, explicit text or JSON output format, Skill selections, and MCP server selections inside the immutable WorkflowVersion while reusing shared Agent runtime infrastructure; JSON mode parses valid final responses and fails invalid JSON. Workflow edges support unconditional, structured predicate, and fallback routing plus optional positive `maxTraversals` bounds; every cycle must cross a bounded edge. Runs use a persisted deterministic sequential scheduler, and nodes with no unbounded incoming edges and no connected required inputs receive the initial invocation; an Agent whose only incoming context edge is bounded can therefore start from Workflow input. Successful execution of the explicit first-party `worklite/artifact` node is the only source of Workflow-created Artifacts; the node owns its Artifact name and text, markdown, or JSON type, persists the Artifact for a successful Run, and exposes an Artifact reference. Agent nodes do not create Artifacts. Plugins and Workflows are peer-level capabilities; Skills and MCP servers serve Workflow Agent nodes and Chat.

Workflow deletion is permanent and removes its draft, edit revisions, published versions, schedule, and run history. Related Artifacts remain available with detached Workflow and Run references.

A failed Workflow Run is retryable at exactly one node: the persisted active invocation, exposed as the `retryable` Node Run flag and `POST /runs/:runId/nodes/:nodeRunId/retry`. Retry re-enters that same Node Run through the existing scheduler-resume path, so successful predecessors are never rerun. Retrying an earlier successful node stays deferred because it would require rolling back committed tokens, edge traversal counts, and downstream Artifacts. This manual command is independent of the per-node `retry` error policy that governs automatic in-run attempts.

WeChat Official Account automation must operate the real WeChat MP pages through Playwright. Do not substitute direct WeChat APIs or captured-session shortcuts for login, draft creation, publishing, or confirmation. Use a headless browser by default; switch to a headed browser only when explicitly requested or needed to debug a confirmed issue.

Classify a WeChat platform response as success or failure before extracting any text from it. `ret: 0`, `errcode: 0`, and `err_msg: "ok"` are success, so treating a present message or code as evidence of failure reports successful operations as rejections. Only after a response is classified as a failure may its `err_msg`, `errmsg`, or status code become user-facing error text.

A missing platform identifier is not the same condition as a platform rejection, and the two must produce different messages. WeChat confirms a saved draft through the editor URL gaining an `appmsgid` query parameter, not only through the save response body, so read the identifier from both and treat the URL as authoritative when the accepted response omits it.

A WeChat draft-mode failure must report the platform's own reason when the browser session exposes one: the failed draft-save response status text, or the text of a blocking editor dialog other than the known content-structure warning. A bare missing-draft-identifier message is the last resort, not the default, because remote runs are otherwise undiagnosable. A publication record that already holds a draft id reopens that draft even while its status is `failed`, so a node retry cannot leave a second draft in the official account.

The WeChat article editor is ProseMirror. It reparses pasted markup against its own schema and discards inline styles, so article HTML is inserted through the editor's own `window.__MP_Editor_JSAPI__` call `mp_editor_set_content` after `mp_editor_get_isready` reports a ready and new editor, with the clipboard paste kept only as a fallback. That content call requires a new editor, so the compose entry point opens the editor with `isNew=1`; a publication that already holds a draft id never refills its body. Calling the editor page's own JSAPI is operating the real MP page and is not a substituted WeChat backend API.

Retained block structure is not evidence of retained styling. A style-stripped article still yields multiple block elements, so a block-count check alone reports an unstyled article as a successful publish. Any pre-save verification must also assert that inline styles survived.

Headless QR login against the real WeChat MP site is verified working, including the `cgi-bin/home?token=` transition. Do not attribute a login failure to headless mode or add user-agent, locale, or other fingerprint overrides without first reproducing the failure and ruling out automation-side causes. WeChat sets the `slave_sid` and `slave_user` cookies about one second before the token page appears, so login confirmation must require the token page; cookie presence alone captures a storage state that has no editor token.


Gateway transport observability is its own `/logs` destination, not part of Providers and not a Settings page. Providers configures what the Gateway dispatches to; Logs reads what it did. Both of its read routes take an explicit absolute `from` and `to` range rather than a named relative window, because a name cannot express an arbitrary interval and a server-resolved name makes a shared link mean a different period for each reader. Statistics are retained indefinitely while request-log details expire after three days, so one shared range legitimately returns different coverage from the two stores; serve the request-log range as its intersection with the retention window and state the truncation rather than failing. Settings keeps Usage and Audit Log, which are WorkLite business records over Runs and resource mutations, not Gateway transport records.

Whenever WorkLite product architecture, resource relationships, supported Workflow nodes, or platform operations change, update the built-in Chat prompt and `worklite-platform` Skill knowledge, scripts, typed tool definitions, and platform snapshot capability metadata in the same change. Chat calls each platform script through the typed tool declared for it in the package's `scripts/tools.json`; that tool's description and input schema are the only contract the model sees, so a script and its tool schema change together. Chat cannot read package reference files, so guidance the model needs belongs in `SKILL.md` or a tool description.

Direct-origin Run answers remain Run evidence and are not projected into the Team transcript. Chat is the master conversation Agent for Web and Feishu. It may inspect and continue Team Runs and dispatch requests through server-owned Team conversation intake; it never bypasses intake, the one-active-Run queue, or non-developer exact command authorization. Feishu replaces WeChat ClawBot chat; the Codex and Claude Code executor plugins and the WeChat Official Account Workflow capability remain independent. External submissions and task bindings are durable; repeated delivery cannot create another task. Starting a Run captures an immutable TeamVersion, Commands from non-developer Team roles require exact-string authorization, and Skills or MCP servers cannot be deleted while referenced by active Team configuration or a captured TeamVersion. New TeamVersions use orchestration version 3: the developer role carries one configuration and no stored instance or concurrency fields; the Planner emits one to four development assignments without developer ids, the runtime maps them in order onto a fixed four-lane pool sharing the role's single captured launch, and the dispatched lane count is Run evidence rather than configuration. Planner assignments own non-overlapping paths, several pending questions are each answered by their own pendingInputId, and a failed fan-out retries through one barrier that resumes every failed assignment without rerunning completed siblings. A role task output that fails validation earns exactly one corrective re-invocation with the parse error fed back before the attempt fails. Team Run progress carries a server-derived completion percentage (terminal-only 100), while Chat project task cards show a server-derived stage without a fabricated percentage.
Feishu Chat defaults to natural dialogue for every new ordinary message. When Chat recognizes the user intent to open a new conversation, show one request-bound new-conversation button. When the user instead asks Chat to run work in another conversation and watch it, Chat starts a background conversation directly through its protected platform tool without waiting for a click, monitors it, and answers its questions itself; the user does not want to be blocked on a button for work Chat can start. ## Git Branch and Worktree Rule

Chat user extensions persist independently of the product-owned base prompt. Capture capabilities per accepted turn and preserve that snapshot for answers and retries. When the user explicitly requests redeployment of WorkLite in Web or Feishu Chat, that request authorizes snapshotting and deploying the current project in the Chat runtime's own profile; do not ask for another card confirmation. Chat invokes the protected redeploy platform script, which binds the actual current user message and immutable release in the independent journal and returns the same job for repeated invocations in that turn. Suggestions, retrieved instructions and historical requests do not authorize a deployment. An independent runner owns the journal outside the API database, performs isolated preflight before touching the current managed runtime, cancels active work after readiness succeeds, and restores matching program and data on candidate failure. Interrupted work is never automatically resumed. Never replay an uncertain operation automatically. A managed installation must establish the previous release baseline before self-upgrade; do not take over unowned processes. Feishu cutover may briefly disconnect and must report its outcome in the originating conversation after reconnect.

Feishu plugin application setup uses the approved one-action QR registration flow based on official `larksuite/cli`: persist encrypted device state across API restart, save credentials automatically after confirmation, never reuse a previous application’s open id, and leave a new app disabled until its own user binding is present. Keep manual existing-application setup and distinguish saved credentials from socket connection. Isolated upgrade preflight must not begin or poll registration.

Research Feishu application credential automation against the official `larksuite/cli` implementation. Keep application registration separate from user OAuth. Do not assume `PersonalAgent` registration also configures message permissions, long-connection subscriptions or publication, and do not overwrite an existing CLI configuration as a credential-import shortcut.

Make authorized project changes directly on the `main` branch in the primary checkout. Do not create feature branches or additional worktrees unless the user explicitly requests them. Preserve existing local changes: inspect the working tree first, and do not commit or discard unrelated work. When the user requests a separate worktree, place it in the parent directory of the primary checkout and name it `../<repository-name>-<purpose>`, such as `../work-lite-workflow-optimization`. This rule governs human-directed development of this repository; the worktrees that Chat project tasks and Team Developer lanes create for their own execution are platform behavior and follow their own `../<repository>-worklite-task-<id>` lifecycle.

## Chat Configuration UI

The Chat workspace has no internal top tabs: its main body stays conversation-only with the history list, transcript and composer. The Chat context bar hides command search and exposes one page-owned settings action in its top-right area. That action opens an accessible Dialog whose internal Channels and Configuration sections retain unframed content; `view=channels` and `view=configuration` deep links open the corresponding section. Slash commands remain shortcuts for visible conversation capabilities and do not replace the settings entry.

Chat's product name and navigation label are `Chat`. `Chat Bot` and `System Helper` are former names and must not be reintroduced in identifiers, copy, documentation, or directory names. The persisted row id `agt_system_helper_chat` and Skill id `sk_worklite_platform` are data rather than naming, and are left unchanged because renaming them requires a migration that would orphan existing executions and Skill assignments.

Chat exposes Cancel for running and ordinary waiting-for-input turns, with immediate control-local progress and retained drafts, messages and effects. Cancel owns a separate pending state and cannot be blocked by send/answer busy state once the server execution exists. Snapshot loading and binding a new execution id must not invalidate pending mutation cleanup; only switching conversations, unmounting or cancellation invalidates older UI completions. Cancelling pauses the queue and stops any linked project task; unresolved operation recovery remains explicit.

Every managed upgrade, whether started by `pnpm deploy:local` or an explicitly authorized Chat redeploy, compiles and readiness-checks the candidate on isolated resources before touching the active deployment. After preflight, cancel active Agent, Team, Workflow, and Command work, stop the owned managed process group immediately, and do not automatically resume interrupted work after success or rollback. Keep matched program/data recovery when candidate startup fails; uncertain external effects still require explicit recovery. `pnpm deploy:local` automatically increments the public product patch version in `apps/web/package.json` before dependency installation and compilation. Every invocation consumes a version even when preflight fails; the old deployed version remains active until preflight succeeds. The command establishes the deployment managed baseline when `.data/deployment/runtime/current.json` is absent. During first migration it may stop only the legacy listener group recorded by `.data/deployment/worklite-local.pid` after verifying that it belongs to this repository's `start-local.mjs`; an unknown or mismatched target listener must remain untouched and make deployment fail. Never create branches, commits, tags or synchronize internal package versions for this counter. The former `install-local.sh`, `start-local.mjs` and `start-background.mjs` paths are retired without compatibility wrappers. Shared composer controls must explicitly compose wrapper-provided click handlers with their own actions; Tooltip props must never overwrite the lower-right Cancel callback.
