# 通过 Chat 更新能力与重新部署 WorkLite

## 更新总 Agent 的能力

Chat 的产品提示词由启动时的内置知识维护。用户扩展提示词单独持久化，不会被这一步覆盖。模型、Skill 和 MCP 选择与扩展提示词一起记录配置修订。

总 Agent 可以通过受保护的 `inspect-chat.mjs`、`update-chat.mjs` 脚本完成配置读取与修改；更新携带刚读到的 `expectedConfigurationRevision`，避免覆盖其间发生的另一次修改。`worklite-platform` Skill 自动保留。

每个新用户轮次保存当时的配置修订、完整提示词、模型、Skill 文件和加密的 MCP 连接配置。该轮后续步骤、问题回答和失败重试继续使用这份快照。更新下一轮生效，不需要为了能力配置重启服务。正在执行或等待回答的轮次仍引用的 Skill/MCP 不能删除。

迁移 `0022_chat_bot_capabilities.sql` 建立配置历史和轮次快照字段。原有历史执行没有快照；其既有读取行为保留，下一次新轮次接受时开始捕获。迁移尚未执行。

## 托管运行基线

对话升级需要先有一个独立的、可启动的旧版本。直接运行当前源码的开发服务没有这个保障，所以升级执行器不会接管已有的未托管进程。

本机部署的唯一操作入口为：

```sh
pnpm deploy:local
```

该命令先递增 Web 补丁版本，再调用托管 runner 的 `deploy deployment`。没有 `.data/deployment/runtime/current.json` 时，runner 快照当前代码，安装依赖并编译候选版本，在 `23490`–`23492` 的隔离端口使用一次性空数据目录做启动就绪预检，不读取或复制部署数据库。Vite 会生成 Web bundle 使用的路由树；runner 在构建和隔离预检期间保存并恢复代码发行快照内的 `apps/web/src/routeTree.gen.ts`，使发行清单继续对应原始代码。若旧 `install-local.sh` 启动的服务占用目标端口，runner 只会在 PID 文件、进程组和监听端口均证明它属于当前项目 `start-local.mjs` 时停止该组；其他占用者会让部署失败，保持原样。通过预检后，runner 直接用部署数据启动 `23390`–`23392` 的托管基线，不做数据备份。若首次启动失败，会尝试停止候选并在成功停止后移除当前运行标记；数据库可能已被启动迁移部分修改，旧服务不会重启，数据也不会恢复。已有基线时，候选版本也先在隔离空数据目录完成编译和就绪检查，随后取消活动 Agent、Team、Workflow、Command 和待处理的飞书应用注册，立即替换托管进程组，不等待任务自然结束。升级不会自动恢复被中断的任务，也不会回滚程序或数据库。切换开始后若候选启动失败，runner 会尝试停止候选并将任务标记为失败；进程归属检查失败时可能仍需人工停止；旧程序不会重启，数据库可能保留部分迁移结果，操作人员需要检查后手动修复或再次部署。每次调用都会消耗一个补丁版本，即使预检失败；当前部署只有在候选版本通过预检后才会切换。

部署状态在 `.data/deployment/runtime/`；开发 Web 仅代理到部署 API，不再拥有 `.data/runtime/` 或独立凭证数据。部署目标端口为 `23390`–`23392`，隔离预检端口为 `23490`–`23492`。旧的 `install-local.sh`、`start-background.mjs` 和 `start-local.mjs` 入口已移除；不要绕过 runner 建立或替换部署服务。

首次启动时应提供与既有数据一致的 `SECRET_ENCRYPTION_KEY` 和所需运行环境。后续升级执行器继承 API 的运行环境。隔离预检使用临时空数据目录；代码发行目录不复制被 Git 忽略的 `.env` 或密钥文件。

托管运行使用独立发行目录中的编译 API 和 Web 产物，保持运行版本与日常编辑目录分离。Chat 将独立代码修改请求交给其 Codex 执行器，协作和独立审查使用 Team；修改在原始项目目录完成，Chat 读取实际任务证据并汇报。部署请求快照该目录中当前存在的已跟踪文件和未忽略新文件，包含未提交的项目修改，不创建 Git 分支或 worktree。发行清单保存文件哈希和模式，当前用户的部署指令绑定整份清单。

## Web 和飞书重新部署请求

用户在 Web 或飞书 Chat 中明确说“重新部署 WorkLite”时，这次指令本身授权当前代码发行快照的依赖安装、编译、隔离空数据预检、中断活动任务和服务切换，不再要求点击确认卡片。Chat 直接调用受保护的 `redeploy.mjs`，只传具体摘要，不将重新部署交给 Codex 或 Team 执行普通命令。服务器从真实当前轮次绑定用户消息，将原文、消息 id、工具调用 id 和不可变发行清单保存到独立日志；同一用户消息重复调用返回同一任务，已失败的任务也不会因此重新执行。只能部署当前托管运行环境的 profile，模型不能传入另一个 profile 或项目路径。

`propose-upgrade.mjs` 仍只生成不执行的提案；建议、历史消息和检索内容不构成部署授权。明确的新部署指令快照当时的项目，而不是自动执行旧提案。旧飞书卡片的升级确认操作已移除，没有兼容回调；直接发送新的重新部署指令。Chat 重新部署仍要求当前 profile 已建立托管基线；操作人员通过 `pnpm deploy:local` 建立并更新该基线。Chat 不接管普通启动的服务。

独立 Node 执行器从这次已授权请求启动，脱离 API 的进程生命周期。请求、授权、中断任务清单和结果保存在 API 数据库之外的升级日志中。Chat 返回任务已经启动后结束本轮，不持续等待或轮询到完成，避免阻塞切换。Web 在原对话任务区自动观察部署阶段，切换期间保留已有状态并重新连接；飞书在同一对话显示任务卡片，并在重连后更新结果。`inspect-upgrade.mjs` 可以读取版本和进度，不返回内部令牌或密钥。

| 阶段 | 行为 |
| --- | --- |
| 隔离预检 | 创建一次性空数据目录；安装并编译候选代码，在隔离端口启动 Web/API/Gateway 并检查就绪。预检禁用飞书外部连接、应用注册轮询、定时任务和 Team 恢复。不会读取或复制当前部署数据库，失败不停止当前服务。 |
| 中断 | 关闭新执行入口；取消活动 Agent、Team、Workflow、Command 和待处理的飞书应用注册；关闭飞书接收并停止托管进程组，不等待活动执行自然结束。不创建数据库、检查点或交付文件备份。 |
| 切换 | 用候选代码直接启动现有 profile 数据，验证发行版本与 Web/API/Gateway 就绪。数据库迁移在原文件上执行。 |
| 失败处理 | 切换失败时按进程归属尝试停止候选并将任务标记为失败；进程归属无法确认时不会强行停止；不启动旧程序，也不恢复数据库。数据库可能有部分迁移，操作人员需检查后修复或重新部署。 |
| 完成与通知 | 新 API 重新建立飞书连接，并在原来的升级卡片报告结果。被中断的任务不会自动恢复；不确定的外部副作用仍需显式核对或恢复。 |

被中断的 Workflow、Team、Agent 和 Command 保留取消状态与已有执行证据。平台副作用不因为“重启了”就自动当成未发生；不确定操作仍要求显式恢复或核对。

飞书入口仍在 API 内，因此切换时允许短暂断连。已接收并落盘的消息、问题、任务引用和交付记录会保留；停机时尚未接收的消息是否重放由飞书决定。持续在线的独立飞书入口没有在本次引入。
