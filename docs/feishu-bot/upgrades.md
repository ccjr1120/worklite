# 通过 Chat 更新能力与重新部署 WorkLite

## 更新总 Agent 的能力

Chat 的产品提示词由启动时的内置知识维护。用户扩展提示词单独持久化，不会被这一步覆盖。模型、Skill 和 MCP 选择与扩展提示词一起记录配置修订。

总 Agent 可以通过受保护的 `inspect-chat.mjs`、`update-chat.mjs` 脚本完成配置读取与修改；更新携带刚读到的 `expectedConfigurationRevision`，避免覆盖其间发生的另一次修改。`worklite-platform` Skill 自动保留。

每个新用户轮次保存当时的配置修订、完整提示词、模型、Skill 文件和加密的 MCP 连接配置。该轮后续步骤、问题回答和失败重试继续使用这份快照。更新下一轮生效，不需要为了能力配置重启服务。正在执行或等待回答的轮次仍引用的 Skill/MCP 不能删除。

迁移 `0022_chat_bot_capabilities.sql` 建立配置历史和轮次快照字段。原有历史执行没有快照；其既有读取行为保留，下一次新轮次接受时开始捕获。迁移尚未执行。

## 托管运行基线

对话升级需要先有一个独立的、可启动的旧版本。直接运行当前源码的开发服务没有这个保障，所以升级执行器不会接管已有的未托管进程。

新的操作入口为：

```sh
node scripts/upgrade-runner.mjs install development
```

这条命令**会安装依赖、构建、启动隔离预检，并在目标端口空闲时启动托管服务**。只有明确授权这些操作后才能执行；本次实施没有执行它。已有端口被占用时，它不会停止监听者。需要替换已有服务时，先取得单独的生命周期授权并通过隔离预检，再由操作人员完成初次交接。已有 `install-local.sh` 的运行方式不自动转换为托管基线。

部署 profile 必须显式指定 `install deployment`，并单独授权。开发状态在 `.data/runtime/`，部署状态在 `.data/deployment/runtime/`；命令不从另一 profile 导入凭证或数据。开发目标端口为 `3390`–`3392`，隔离预检端口为 `3490`–`3492`；部署目标为 `23390`–`23392`，隔离预检为 `23490`–`23492`。

首次启动时应提供与既有数据一致的 `SECRET_ENCRYPTION_KEY` 和所需运行环境。后续升级执行器继承 API 的运行环境，并在切换和回滚时保持它。升级副本不复制被 Git 忽略的 `.env` 或密钥文件。

托管运行使用独立发行目录中的编译 API 和 Web 产物，保持运行版本与日常编辑目录分离。Chat 将独立代码修改请求交给其 Codex 执行器，协作和独立审查使用 Team；修改在原始项目目录完成，Chat 读取实际任务证据并汇报。部署请求快照该目录中当前存在的已跟踪文件和未忽略新文件，包含未提交的项目修改，不创建 Git 分支或 worktree。发行清单保存文件哈希和模式，当前用户的部署指令绑定整份清单。

## Web 和飞书重新部署请求

用户在 Web 或飞书 Chat 中明确说“重新部署 WorkLite”时，这次指令本身授权当前项目快照的依赖安装、编译、隔离预检、任务交接、备份、服务切换和失败恢复，不再要求点击确认卡片。Chat 直接调用受保护的 `redeploy.mjs`，只传具体摘要，不将重新部署交给 Codex 或 Team 执行普通命令。服务器从真实当前轮次绑定用户消息，将原文、消息 id、工具调用 id 和不可变发行清单保存到独立日志；同一用户消息重复调用返回同一任务，已失败的任务也不会因此重新执行。只能部署当前托管运行环境的 profile，模型不能传入另一个 profile 或项目路径。

`propose-upgrade.mjs` 仍只生成不执行的提案；建议、历史消息和检索内容不构成部署授权。明确的新部署指令快照当时的项目，而不是自动执行旧提案。旧飞书卡片的升级确认操作已移除，没有兼容回调；直接发送新的重新部署指令。首次托管基线仍由操作人员建立，Chat 不接管普通启动的服务。

独立 Node 执行器从这次已授权请求启动，脱离 API 的进程生命周期。请求、授权、交接任务、备份状态和结果保存在 API 数据库之外的升级日志中。Chat 返回任务已经启动后结束本轮，不持续等待或轮询到完成，避免阻塞交接。Web 在原对话任务区自动观察部署阶段，切换期间保留已有状态并重新连接；飞书在同一对话显示任务卡片，并在重连后更新结果。`inspect-upgrade.mjs` 可以读取版本和进度，不返回内部令牌或密钥。

| 阶段 | 行为 |
| --- | --- |
| 隔离预检 | 安装并编译候选代码；复制当前 profile 的数据，SQLite 使用在线备份；启动候选的 Web/API/Gateway 并检查就绪。禁用飞书外部连接、应用注册轮询、定时任务和 Team 恢复，避免双重执行。失败不停止当前服务。 |
| 交接 | 关闭新执行入口；等待活动对话完成；通过已有 API 暂停 Team 和活动 Workflow；等待运行时与 Commands 到达持久化边界，并等待已发起的应用注册请求结束。等待中的问题和加密 QR 注册状态保留，注册轮询在交接期间暂停。超时不替换服务。 |
| 冻结与备份 | 关闭飞书接收，等待已进入适配器的工作结束，阻止其他 HTTP 操作；停止已确认归属的托管进程后，备份数据库、检查点和交付文件。此时没有服务再写数据库。 |
| 切换 | 用候选代码和原 profile 数据启动服务，验证发行版本与 Web/API/Gateway 就绪。 |
| 恢复 | 切换失败时恢复匹配的旧发行目录和备份数据；不让旧程序读取升级后的数据库。恢复失败仍保留日志和恢复阶段，供本机继续处理。 |
| 继续与通知 | 新 API 或恢复后的 API 只继续本次升级交接的暂停任务，重新建立飞书连接，并在原来的升级卡片报告结果。任务继续失败时保留交接标记并重试恢复，不重新执行升级。 |

Workflow 暂停后的继续仍遵循现有 scheduler：成功前驱不会重跑，暂停的活动调用按现有语义重新进入。Team 使用已有持久化检查点和 uncertain operation 恢复输入。平台副作用不因为“重启了”就自动当成未发生。

飞书入口仍在 API 内，因此切换时允许短暂断连。已接收并落盘的消息、问题、任务引用和交付记录会保留；停机时尚未接收的消息是否重放由飞书决定。持续在线的独立飞书入口没有在本次引入。
