# Agent task continuation

Chat selects an action before selecting a session. Status, progress and error explanations read existing records. Stop/cancel requests use controls. Independent goals use `run_agent` with `mode: new`, even for the same Agent or project. A mention identifies a target and never implies continuation.

Only a follow-up to the same task uses `mode: continue`, its exact `executionId` and a `continuationReason` describing the task and new input. Multiple possible tasks require clarification. Cancelled tasks additionally require `resumeCancelled: true`, reflecting an explicit user request. Running or pending-input instances use their existing controls/questions. Failure is inspected before deciding whether to resume; uncertain writes are not automatically replayed.

Continuation appends only the new requirement. It does not copy the tool-call table into model history. Legacy `[Saved instance tool evidence]` snapshots are removed on continuation or recovery, including copies in merged user part arrays; user text, tool exchanges and stored tool records remain. The original history is archived as an execution-scoped `agent_capability_results` value before replacement. Recovery repairs missing tool results by call ID rather than rerunning tools.

When the upstream rejects a context as too long, a model-only checkpoint summarizes old history, keeping the latest user message intact. Large historical data is summarized in chunks. Archives must persist before model history is replaced. Only the current model request is retried, at most twice; the workflow/tool loop is not restarted. A failed summary, archive write, oversized latest message or unresolved upstream limit produces an explicit context error and retains the available evidence. Checkpoints are summaries, not independently verified evidence; completed and uncertain writes must not be replayed. They preserve task goals, changed requirements, completed and unfinished work, exact evidence references and blockers. No local context-token ceiling is imposed by this recovery mechanism.

Native leads and their sub-Agents read archives with `read_result`. Chat and operators can page archives using authenticated `GET /agents/:agentId/executions/:executionId/history-archives/:resultRef?offset=0&maxChars=12000`; workspace, Agent and execution must match. Archives do not add UI fields. Full execution/tool records remain separate from compacted model context.

OpenAI/Codex requests no longer receive a default local output-token ceiling. Anthropic still receives the protocol-required `max_tokens` (64,000 by default); an explicit output setting overrides it. Output overrides accept positive safe integers rather than a 100,000-token application ceiling. Provider context/output capacity and quotas remain in force.
